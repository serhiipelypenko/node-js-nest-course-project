# Restore-drill — протокол

Тут зафіксовано
реальний прогін `scripts/backup.sh` → `scripts/restore-drill.sh`.

## Прогін

| Параметр | Значення |
|----------|----------|
| Дата | 2026-09-20 |
| Команди | `bash scripts/with-secrets.sh dev bash scripts/backup.sh`, потім `bash scripts/with-secrets.sh dev bash scripts/restore-drill.sh` (під `SKIP_VAULT=1`) |
| Середовище | локальна машина (Apple Silicon), Docker Desktop, `postgres:16-alpine`, PgBouncer 1.24 |
| База | `marketplace`, датасет hw-12: 300 000 замовлень, 600 000 позицій, 20 000 покупців, 2 000 товарів |
| Дамп | `backups/marketplace-2026-09-20_214605.dump` — **13 563 484 байт (≈ 12,9 МіБ)**, `pg_dump -Fc`, 29 обʼєктів у TOC |
| Куди відновлено | чистий контейнер `marketplace-restore-drill` (той самий образ, що й `db`) з новим порожнім томом; 0 таблиць до `pg_restore` |
| Підйом чистого контейнера | 1,7 с |
| `pg_restore` | 1,4 с |
| **Виміряний RTO drill-у** | **3,3 с** (контейнер + `pg_restore` + звірка) |
| Контрольні значення до | `order_items=600000, orders=300000, products=2000, users=20000`; `sum(total_amount)=150725353.55` |
| Контрольні значення після | ті самі |
| Результат | **MATCH**, exit 0 |

Менший датасет (міграції hw-13/14 + `npm run seed`: 38 замовлень, дамп 16 813 байт)
дав RTO 1,6–1,7 с — майже весь час це старт контейнера, а не відновлення.
Повторний запуск теж дає MATCH (скрипт сам створює і сам прибирає контейнер разом
із томом). Негативний прогін — після бекапу змінили одне замовлення
(`total_amount + 1`) — дає `MISMATCH` і exit 1, тобто звірка справді ловить розбіжність.

## RTO

**RTO ≈ 3,3 секунди** — це виміряне на drill-і: час від `docker run` чистого
контейнера до збіжної контрольної суми. Чесні застереження:

- Це нижня межа: образ `postgres:16-alpine` уже був локально, дамп лежав на
  локальному диску, база — 13 МБ. З віддаленого сховища додається час завантаження
  дампу, на холодній машині — `docker pull` (десятки секунд).
- Drill не міряє все, що входить у реальний RTO інциденту: час, поки хтось помітить
  проблему й почне відновлення, та перемикання застосунку на відновлену базу
  (`DB_URL`/PgBouncer). Орієнтовна оцінка з ними: **до ~15 хвилин** (оцінка, не вимір).
- Час відновлення росте з розміром бази лінійно-ish: `pg_restore` 13 МБ = 1,4 с, тож
  умовні 10 ГБ — порядку **хвилин** (оцінка; індекси перебудовуються при відновленні).

## RPO

**RPO = до 24 години** — це розрахунок з розкладу `backup.cron` (`0 3 * * *`, щоночі
о 03:00): якщо база загине о 02:59, остання точка відновлення — вчорашні 03:00, тобто
втрачається майже доба записів (у середньому ≈ 12 годин). У drill-і скрипт друкує
вік використаного дампу (тут 0 с, бо дамп зроблено безпосередньо перед drill-ом) —
це вимір стану на момент drill-у, а не гарантія розкладу.

Якщо 24 години втрат неприйнятні: частіший `pg_dump` (щогодини → RPO до 1 год) або
WAL-архів + PITR (RPO — секунди/хвилини), але це вже поза цим ДЗ.

## Що drill не доводить

- Відновлення йде без ролей і GRANT-ів (`--no-owner --no-acl`): у чистому контейнері
  немає службової ролі `pgbouncer_auth`. Дані, схема й індекси відновлюються повністю;
  ролі на новому сервері треба створювати окремо (`scripts/init.sql`).
- Дамп зроблено з живої бази без зупинки записів — `pg_dump` бере узгоджений знімок,
  тож MATCH порівнює дамп із базою на момент бекапу. Якщо між `backup.sh` і drill-ом
  у базу пишуть, контрольні значення розійдуться (це і є MISMATCH з негативного прогону).
